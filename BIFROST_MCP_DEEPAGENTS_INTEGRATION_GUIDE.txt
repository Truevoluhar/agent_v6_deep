# Bifrost MCP Tools -> DeepAgents Integration Guide
Repository: https://github.com/Truevoluhar/agent_v6_deep
Prepared: 2026-10-02

## Goal

Your MCP servers are already connected to Bifrost. The goal is to make those tools available as first-class tools inside the DeepAgents runtime in `agent_v6_deep`, while continuing to use Bifrost as the LLM gateway.

Recommended architecture:

    User / Streamlit client
             |
             v
        agent-api
             |
             v
       DeepAgents runtime
          /         \
         /           \
        v             v
    Bifrost LLM    Bifrost MCP
    /openai        /mcp
       |              |
       v              v
    LLM provider   MCP servers

The important point is that Bifrost can act as BOTH:
1. an OpenAI-compatible inference gateway; and
2. an MCP server that aggregates the MCP servers already configured in Bifrost.

So you do NOT need to register every MCP server a second time in DeepAgents.
DeepAgents can connect once to Bifrost's `/mcp` endpoint and receive the aggregated tool list.

Bifrost documentation confirms that Bifrost exposes configured MCP tools through:
    http://<bifrost-host>:8080/mcp

Your existing model URL is:
    http://<bifrost-host>:8080/openai

These are sibling endpoints. Do not use `/openai/mcp`.

-------------------------------------------------------------------------------
1. CURRENT REPO INTEGRATION POINT
-------------------------------------------------------------------------------

In the current repository, `agent_api/runtime.py` builds the DeepAgent.

Relevant existing logic is approximately:

    agent_kwargs = {
        "model": build_chat_model(self.config.provider),
        "tools": self.tool_collection.tools,
        "system_prompt": self.build_system_prompt(),
        ...
    }

That means the correct place to add Bifrost MCP tools is the `tools` collection supplied to `create_deep_agent()`.

Target:

    tools = [
        *self.tool_collection.tools,
        *self.mcp_tools,
    ]

Do not replace the existing internal tools. Merge the MCP tools with them.

    agent_api/requirements.txt

Add:

    langchain-mcp-adapters

Your current requirements include `deepagents==0.7.15` and LangChain/OpenAI packages.
After testing, pin `langchain-mcp-adapters` to the version you deploy in production.

Rebuild the service after changing requirements:

    docker compose build agent-api
    docker compose up -d agent-api

-------------------------------------------------------------------------------
3. ENVIRONMENT VARIABLES
-------------------------------------------------------------------------------

Add these to `.env.example`:

    BIFROST_MCP_ENABLED=true
    BIFROST_MCP_URL=http://host.docker.internal:8080/mcp
    BIFROST_MCP_API_KEY=dummy-key

If Bifrost is another Docker Compose service on the same Docker network, use its
service name instead, for example:

    BIFROST_MCP_URL=http://bifrost:8080/mcp

For production:

    BIFROST_MCP_URL=https://bifrost.example.com/mcp
    BIFROST_MCP_API_KEY=<your Bifrost virtual key>

If your Bifrost `/mcp` endpoint does not require authentication, the auth header
can be omitted. For authenticated Bifrost deployments, the MCP endpoint accepts
Bifrost credentials such as an Authorization Bearer virtual key.

Do not hard-code secrets in the repository.

-------------------------------------------------------------------------------
4. CONFIG MODEL CHANGES
-------------------------------------------------------------------------------

In `agent_api/config.py`, extend `AgentConfig`.

Example:

    @dataclass(frozen=True)
    class AgentConfig:
        ...
        bifrost_mcp_enabled: bool
        bifrost_mcp_url: str | None
        bifrost_mcp_api_key: str | None

Then in `load_config()`:

    bifrost_mcp_enabled = (
        env_values.get("BIFROST_MCP_ENABLED", "false")
        .strip()
        .lower()
        in {"1", "true", "yes", "on"}
    )

    bifrost_mcp_url = (
        env_values.get("BIFROST_MCP_URL", "").strip() or None
    )

    bifrost_mcp_api_key = (
        env_values.get("BIFROST_MCP_API_KEY", "").strip() or None
    )

Add these fields when constructing `AgentConfig`:

    agent = AgentConfig(
        ...
        bifrost_mcp_enabled=bifrost_mcp_enabled,
        bifrost_mcp_url=bifrost_mcp_url,
        bifrost_mcp_api_key=bifrost_mcp_api_key,
    )

You may alternatively derive `/mcp` from `BIFROST_BASE_URL`, but a separate
variable is safer because `BIFROST_BASE_URL` currently ends in `/openai`.

-------------------------------------------------------------------------------
5. WHY THE AGENT SHOULD BECOME ASYNC
-------------------------------------------------------------------------------

The current repository calls:

    agent.invoke(...)

MCP tools produced by `langchain-mcp-adapters` are normally async tools.
Using them through a synchronous graph invocation can produce:

    NotImplementedError:
    StructuredTool does not support sync invocation.

Therefore use:

    await agent.ainvoke(...)

This requires the request path that invokes the runtime to become async.

-------------------------------------------------------------------------------
6. ADD BIFROST MCP CLIENT TO AgentRuntime
-------------------------------------------------------------------------------

Recommended approach: discover tools once when the application starts, store the
LangChain tool wrappers on the runtime, and reuse them.

Modify `agent_api/runtime.py`.

Add imports:

    from dataclasses import dataclass, field
    from langchain_core.tools import BaseTool
    from langchain_mcp_adapters.client import MultiServerMCPClient

Extend the runtime:

    @dataclass
    class AgentRuntime:
        config: AppConfig
        workspace: WorkspaceManager
        process_manager: BackgroundProcessManager
        shell_env: dict[str, str]
        tool_collection: ToolCollection

        mcp_client: MultiServerMCPClient | None = None
        mcp_tools: list[BaseTool] = field(default_factory=list)

Keep `create()` mostly as it is.

Then add:

    async def initialize_mcp(self) -> None:
        if not self.config.agent.bifrost_mcp_enabled:
            return

        url = self.config.agent.bifrost_mcp_url
        if not url:
            raise ValueError(
                "BIFROST_MCP_ENABLED=true but BIFROST_MCP_URL is empty."
            )

        headers = {}
        if self.config.agent.bifrost_mcp_api_key:
            headers["Authorization"] = (
                f"Bearer {self.config.agent.bifrost_mcp_api_key}"
            )

        connection = {
            "url": url,
            "transport": "streamable_http",
        }

        if headers:
            connection["headers"] = headers

        self.mcp_client = MultiServerMCPClient(
            {
                "bifrost": connection,
            },
            # Optional but useful if Bifrost exposes duplicate tool names:
            tool_name_prefix=True,
            handle_tool_errors=True,
        )

        self.mcp_tools = await self.mcp_client.get_tools()

`MultiServerMCPClient.get_tools()` creates LangChain-compatible tools.

Because Bifrost itself aggregates your MCP servers, DeepAgents only needs this
single connection.

-------------------------------------------------------------------------------
7. MERGE INTERNAL + MCP TOOLS
-------------------------------------------------------------------------------

In `AgentRuntime`, add a helper:

    def all_tools(self):
        return [
            *self.tool_collection.tools,
            *self.mcp_tools,
        ]

Then change:

    "tools": self.tool_collection.tools,

to:

    "tools": self.all_tools(),

This gives the DeepAgent:

- your existing filesystem/shell/custom toolkits;
- DeepAgents built-in tools;
- every allowed MCP tool exposed by Bifrost.

-------------------------------------------------------------------------------
8. CONVERT AgentRuntime.invoke() TO ASYNC
-------------------------------------------------------------------------------

Change:

    def invoke(self, thread_id: str, message: str) -> Any:

to:

    async def invoke(self, thread_id: str, message: str) -> Any:

Keep the existing `create_deep_agent(...)` construction.

Change both graph calls from:

    return agent.invoke(...)

to:

    return await agent.ainvoke(...)

Example:

    return await agent.ainvoke(
        {"messages": [{"role": "user", "content": message}]},
        config={
            "configurable": {"thread_id": thread_id},
            "recursion_limit": self.config.agent.recursion_limit,
        },
    )

Do this in both the checkpointer and non-checkpointer branches.

-------------------------------------------------------------------------------
9. INITIALIZE MCP DURING FASTAPI STARTUP
-------------------------------------------------------------------------------

The current `agent_api/main.py` has a synchronous startup handler.

Change:

    @app.on_event("startup")
    def startup() -> None:
        app.state.runtime = AgentRuntime.create(load_config())

to:

    @app.on_event("startup")
    async def startup() -> None:
        runtime = AgentRuntime.create(load_config())
        await runtime.initialize_mcp()
        app.state.runtime = runtime

This causes MCP tool discovery to happen once when `agent-api` starts instead of
performing an MCP handshake for every chat message.

-------------------------------------------------------------------------------
10. MAKE THE MESSAGE ENDPOINT ASYNC
-------------------------------------------------------------------------------

The current route is synchronous and calls:

    result = runtime.invoke(...)

Change:

    @app.post("/v1/threads/{thread_id}/messages", ...)
    def post_thread_message(...):

to:

    @app.post("/v1/threads/{thread_id}/messages", ...)
    async def post_thread_message(...):

Then:

    result = await runtime.invoke(
        thread_id=thread_id,
        message=request.message,
    )

IMPORTANT:
The current code uses `threading.Lock()` around invocation. Do not hold a
threading lock across `await`.

Either:

A. remove the global serialization lock if LangGraph/checkpointing already
   provides sufficient thread isolation; or

B. use an asyncio lock.

Minimal replacement:

    import asyncio

    THREAD_LOCK = asyncio.Lock()

and:

    async with THREAD_LOCK:
        result = await runtime.invoke(
            thread_id=thread_id,
            message=request.message,
        )

A single global lock serializes all users, so a better production design is one
async lock per thread_id.

-------------------------------------------------------------------------------
11. OPTIONAL: SHOW MCP TOOLS IN /v1/tools
-------------------------------------------------------------------------------

Currently `/v1/tools` returns only internal toolkits.

It is useful to expose diagnostics.

Example:

    @app.get("/v1/tools")
    def get_tools() -> dict[str, Any]:
        runtime = get_runtime()
        return {
            "toolkits": runtime.tool_collection.toolkits,
            "mcp_tools": [
                {
                    "name": tool.name,
                    "description": tool.description,
                }
                for tool in runtime.mcp_tools
            ],
        }

Do not expose secrets, headers, OAuth tokens, or MCP connection credentials.

-------------------------------------------------------------------------------
12. FULL MINIMAL RUNTIME PATTERN
-------------------------------------------------------------------------------

A simplified implementation looks like this:

    from __future__ import annotations

    from dataclasses import dataclass, field
    from typing import Any

    from langchain_core.tools import BaseTool
    from langchain_mcp_adapters.client import MultiServerMCPClient

    @dataclass
    class AgentRuntime:
        ...
        mcp_client: MultiServerMCPClient | None = None
        mcp_tools: list[BaseTool] = field(default_factory=list)

        async def initialize_mcp(self) -> None:
            if not self.config.agent.bifrost_mcp_enabled:
                return

            headers = {}
            if self.config.agent.bifrost_mcp_api_key:
                headers["Authorization"] = (
                    f"Bearer {self.config.agent.bifrost_mcp_api_key}"
                )

            connection = {
                "url": self.config.agent.bifrost_mcp_url,
                "transport": "streamable_http",
            }
            if headers:
                connection["headers"] = headers

            self.mcp_client = MultiServerMCPClient(
                {"bifrost": connection},
                tool_name_prefix=True,
                handle_tool_errors=True,
            )
            self.mcp_tools = await self.mcp_client.get_tools()

        def all_tools(self):
            return [*self.tool_collection.tools, *self.mcp_tools]

        async def invoke(self, thread_id: str, message: str) -> Any:
            from deepagents import create_deep_agent
            from deepagents.backends import LocalShellBackend
            from agent_api.model_factory import build_chat_model

            agent_kwargs = {
                "model": build_chat_model(self.config.provider),
                "tools": self.all_tools(),
                "system_prompt": self.build_system_prompt(),
                "backend": LocalShellBackend(
                    root_dir=self.config.agent.workspace_root,
                    virtual_mode=True,
                    inherit_env=False,
                    timeout=self.config.agent.shell_timeout_seconds,
                    env=self.shell_env,
                ),
                "memory": self.config.agent.memory_files,
                "skills": [self.config.agent.skills_root],
            }

            agent = create_deep_agent(**agent_kwargs)

            return await agent.ainvoke(
                {"messages": [{"role": "user", "content": message}]},
                config={
                    "configurable": {"thread_id": thread_id},
                    "recursion_limit": self.config.agent.recursion_limit,
                },
            )

Keep your existing Postgres checkpointer branch; only switch its final graph
execution to `await agent.ainvoke(...)`.

-------------------------------------------------------------------------------
13. BIFROST-SIDE SETTINGS
-------------------------------------------------------------------------------

Your MCP servers remain registered in Bifrost.

In Bifrost, verify:

1. MCP is enabled.
2. The MCP clients are connected and healthy.
3. The tools you want are enabled.
4. `tools_to_execute` allows them.
5. `/mcp` is reachable from the `agent-api` container.
6. Authentication is configured correctly.

Bifrost supports its own inbound MCP server at:

    http://<bifrost-host>:8080/mcp

Bifrost can apply centralized:
- tool filtering;
- virtual-key permissions;
- authentication;
- per-user header/OAuth handling;
- tool execution policies;
- observability.

That is why using Bifrost's aggregated `/mcp` endpoint is preferable to copying
all of the individual MCP server definitions into `agent_v6_deep`.

-------------------------------------------------------------------------------
14. IMPORTANT: DO NOT ENABLE TWO TOOL-ORCHESTRATION PATHS ACCIDENTALLY
-------------------------------------------------------------------------------

There are two conceptually different ways to use Bifrost MCP.

PATH A - RECOMMENDED FOR DEEPAGENTS

    DeepAgent -> Bifrost /mcp -> MCP server

DeepAgents sees each MCP tool, chooses it, and executes it through the MCP
adapter.

Use this when you want:
- DeepAgents/LangGraph to own orchestration;
- tool calls visible in the agent graph;
- normal tool errors and retries;
- checkpoint/HITL integration;
- one consistent DeepAgents tool registry.

PATH B - BIFROST AUTO-INJECTION / AGENT MODE

    DeepAgent model request -> Bifrost /openai
                              -> Bifrost injects MCP tools
                              -> Bifrost may manage execution

Bifrost can inject MCP tools into inference requests and also supports MCP agent
mode / auto-execution.

If you simultaneously expose the same tools to DeepAgents through `/mcp`, the
model may receive duplicate or competing tool definitions.

Recommended configuration when using PATH A:
- DeepAgents connects to Bifrost `/mcp`.
- Disable automatic Bifrost MCP tool injection for model inference requests, or
  otherwise ensure those MCP tools are not injected into requests originating
  from `agent_v6_deep`.

Bifrost has a `disable_auto_tool_inject` MCP tool-manager setting. If set to
true, MCP tools are not automatically injected into ordinary inference calls.

Conceptually:

    mcp:
      tool_manager_config:
        disable_auto_tool_inject: true

This keeps responsibilities clear:

    Bifrost /openai = LLM routing
    Bifrost /mcp    = tool gateway
    DeepAgents      = orchestration

-------------------------------------------------------------------------------
15. TOOL FILTERING
-------------------------------------------------------------------------------

Do not automatically give a general-purpose agent every powerful MCP tool.

Prefer least privilege.

Bifrost can filter tools by MCP client / tool and can enforce permissions via
virtual keys.

A good design is to create a Bifrost virtual key specifically for this agent,
and allow only the MCP tools this agent should use.

For example:

    agent_v6_deep
        |
        | Authorization: Bearer <agent-specific-Bifrost-key>
        v
      Bifrost /mcp
        |
        +-- read-only CRM tools
        +-- approved search tools
        +-- approved ticket tools

Do not expose destructive admin/database/filesystem tools unless the agent truly
needs them.

-------------------------------------------------------------------------------
16. DUPLICATE TOOL NAMES
-------------------------------------------------------------------------------

Multiple MCP servers may expose the same tool name, such as:

    search
    get
    list
    create

Use:

    tool_name_prefix=True

when constructing `MultiServerMCPClient`.

Because DeepAgents sees Bifrost as one MCP server, Bifrost itself should already
avoid ambiguous exported names where possible. Still inspect the resulting
names through `/v1/tools`.

-------------------------------------------------------------------------------
17. AUTHENTICATION / USER-SPECIFIC MCP TOOLS
-------------------------------------------------------------------------------

If your MCP tools need static service authentication:
- keep those secrets in Bifrost;
- let Bifrost authenticate to the underlying MCP server.

If tools need user-specific credentials:
- Bifrost supports per-user OAuth and per-user headers for MCP clients;
- Bifrost can forward allowed request/session headers to the downstream MCP
  server.

This requires more design than using one service-level token because your
agent-api needs to propagate the user/session identity to Bifrost's `/mcp`
connection.

Do not put end-user OAuth tokens into prompts or LangGraph state.

-------------------------------------------------------------------------------
18. DOCKER NETWORK CHECK
-------------------------------------------------------------------------------

From inside the `agent-api` container, test that Bifrost is reachable.

If Bifrost runs on the Docker host:

    docker compose exec agent-api \
      curl -i http://host.docker.internal:8080/mcp

If Bifrost runs as a Compose service named `bifrost`:

    docker compose exec agent-api \
      curl -i http://bifrost:8080/mcp

An MCP endpoint may not return a useful response to a plain GET, but connection
errors immediately reveal DNS/network problems.

Also verify your virtual key/auth configuration if you get 401/403.

-------------------------------------------------------------------------------
19. TESTING
-------------------------------------------------------------------------------

A. Discovery test

Temporarily log tool names after startup:

    print(
        "Loaded MCP tools:",
        [tool.name for tool in runtime.mcp_tools],
    )

Expected:
- non-empty list;
- tools correspond to those visible in Bifrost.

B. API diagnostic

    curl http://localhost:8081/v1/tools

Expected:
- internal toolkits;
- MCP tools if you added the diagnostic output.

C. Natural-language tool call

Ask the agent something that can ONLY be answered by one of your MCP tools.

Example:

    "Use <specific MCP tool capability> to fetch ..."

Expected sequence:
1. DeepAgent sends model request through Bifrost `/openai`.
2. Model chooses the MCP-derived LangChain tool.
3. DeepAgents invokes the tool wrapper.
4. Wrapper calls Bifrost `/mcp`.
5. Bifrost calls the configured upstream MCP server.
6. Tool result returns to DeepAgents.
7. DeepAgent continues reasoning and answers.

D. Failure test

Disable the MCP server in Bifrost and repeat.

Expected:
- tool failure is surfaced to the agent;
- agent-api does not crash;
- with `handle_tool_errors=True`, normal MCP tool execution errors are returned
  as tool errors the agent can potentially recover from.

20. TROUBLESHOOTING
-------------------------------------------------------------------------------

Problem:
    MCP tools are visible but calling one gives:
    "StructuredTool does not support sync invocation"

Cause:
    The graph is running through `.invoke()`.

Fix:
    Use `.ainvoke()` and make the FastAPI route/runtime async.

---

Problem:
    No MCP tools are loaded.

Check:
- BIFROST_MCP_ENABLED
- BIFROST_MCP_URL
- network/DNS from agent-api container
- Bifrost MCP health/configuration
- Bifrost virtual-key permissions
- MCP server tool enablement

---

Problem:
    401 or 403 from `/mcp`.

Fix:
    Pass the correct Bifrost credential, for example:

        headers = {
            "Authorization": "Bearer <virtual-key>"
        }

Check Bifrost's `mcp_server_auth_mode` and auth settings.

---

Problem:
    The model sees duplicate tools.

Cause:
    The same Bifrost MCP tools are being:
    1. registered in DeepAgents via `/mcp`; AND
    2. automatically injected by Bifrost into `/openai` inference requests.

Fix:
    Use one orchestration path. For this architecture, prefer DeepAgents as the
    orchestrator and disable Bifrost auto tool injection for those inference
    requests/configuration.

---

Problem:
    Tool list is huge and model performance/cost suffers.

Options:
- restrict the agent-specific Bifrost virtual key;
- enable only needed MCP clients/tools;
- use separate agent profiles with different tool sets;
- consider Bifrost Code Mode for very large MCP installations, but note that
  this changes the tool interface and orchestration model.

25. FINAL RECOMMENDATION
-------------------------------------------------------------------------------

For this repository, use this ownership split:

    DeepAgents
        owns planning, tool selection, execution loop, checkpointing,
        subagents, and HITL

    Bifrost /openai
        owns LLM/provider routing

    Bifrost /mcp
        owns MCP aggregation, MCP credentials, permissions, filtering,
        governance, and forwarding to the real MCP servers

This gives you one tool gateway, without registering every MCP server twice,
while still making every allowed MCP tool a native DeepAgents tool.
